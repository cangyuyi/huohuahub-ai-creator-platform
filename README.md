## 业务背景

HuohuaHub 平台早期建设阶段，运营者每周被困在三件事里：

1. **周复盘耗时**：7 张飞书表手动汇总数据、翻访谈记录写画像，每次 2 小时以上
2. **话术凭感觉**：邀约话术无法复用经验，效果好坏全靠个人手感
3. **课件搜不到**：40 天课程的 528 张课件是图片格式，重复答疑占社群问题 60%

平台早期也有定位和使用问题——Skill 商店被埋没在二级页面，80% 用户不知道它的存在；Top 创作者两周后不再上传。

## 用户调研

通过 24 份问卷 + 访谈，推翻了四个初始假设：

| 我们假设 | 调研发现 | 转向 |
|----------|----------|------|
| 用户需要系统课程 | 67% 反馈「太笼统」，点击率 <5% | 场景化即用方案 |
| Skill 商店是附加功能 | 80% 不知道有 Skill 库 | 提至首页核心位 |
| 发课就是运营 | 重复问题占答疑 60% | OCR + RAG 问答机器人 |
| 创作者靠热情留存 | Top 创作者 2 周后不再上传 | 身份认证 + 成长体系 |

关键数据：直接问需求的邀约回复率 66%，泛泛「学习搭子」互动率仅 3%。

## 用户场景

- **目标用户**：HuohuaHub 的运营者、平台创作者、课程用户，以及参与平台日常执行的实习生
- **核心场景**：
  1. **运营者周复盘**：每周从飞书多维表格拉取投放数据，AI 生成群体画像和话术建议，从 2 小时压缩到 3 分钟
  2. **创作者提问（公众号 RAG）**：在公众号接入课件知识库，支持出处引用和超纲拒答；15 题评测集从 5/15 优化到 15/15
  3. **实习生执行 SOP**：每日按工作台查看任务、勾选完成、提交打卡，Mentor 验收
- **边界**：不做内容创作工具（那是创作者自己的事）、不做社区 feed 流推荐（聚焦运营效率）

## 人机方案

| 环节 | AI/系统负责 | 人负责 |
|------|------------|--------|
| 周复盘 | 自动汇总数据 + 访谈，生成 9 段式群体画像 | 确认画像、制定运营策略 |
| 话术生成 | 画像驱动生成 3 条不同风格话术，自动写回飞书 | 审核后发送 |
| 课件问答 | RAG 检索 528 张课件，带出处回答 | 超纲问题转人工 |
| AI 日报 | 自动搜集新闻 + AI 主编筛选 + 漫画生成 + 排版推送 | 确认每日内容质量 |
| 任务执行 | 飞书工作台自动分配任务、汇总状态 | 完成任务、一键勾选 |

关键设计：话术生成器强制 JSON 输出（固定字段结构），因为要自动写回飞书不同字段；超纲问题拒答而非编造。

## 平台模块一：AI 运营平台（团队实际使用）

把运营者每周「汇总数据 → 翻访谈 → 写画像 → 写话术 → 录入文案库」的 2 小时手动流程，重构为 Dify 上的自动化流程，供团队全员使用，主要服务每周运营复盘。

| 应用 | 类型 | 做什么 | 关键设计 |
|------|------|--------|----------|
| 周画像生成器 | Workflow | 投放数据 + 访谈 → 9 段式群体画像报告 | 每个痛点附访谈原话作证据 |
| 话术生成器 | Workflow | 画像驱动生成 3 条不同风格话术 | JSON 输出，Code 解析后自动写回飞书 |
| 主控 Workflow | Workflow | 8 节点 HTTP 串联画像 → 话术全链路 | Code 节点 json.dumps 解决转义 |

> 问答助手（RAG 问答）见下方[平台模块二](#平台模块二rag-问答机器人dify--公众号实际接入)，它从 Dify 搭建演进到微信公众号实际接入。

**实际使用结果**：周复盘耗时由 2 小时压缩到 3 分钟；画像和话术按固定格式写回飞书文案库；将人工运营投放链路封装为 AI Workflow 后，内容迭代周期由 11 天缩短至 6 天。

## 平台模块二：RAG 问答机器人（公众号实际接入，低频使用）

同一个问答机器人的两个阶段：先在 Dify 上搭建，再接入微信公众号，知识库从 16 篇文档扩展到 528 张课件 OCR。公众号实际使用量不高，但已经进入真实业务链路。

### 阶段一：Dify 搭建（问答助手）

在 Dify 上用 Chatflow 搭建 RAG 问答助手，验证社群问答场景：

- RAG 检索 16 篇运营文档，带出处回答社群问题
- TopK=3，相似度阈值 0.5，超纲问题拒答而非编造
- 20 题黄金集评测（学习路径 / 工具推荐 / 社群活动 / 话术查询），通过率 90%（18/20）

### 阶段二：微信公众号实际接入（课件问答机器人）

验证可行后，将 40 天课程的 528 张课件 OCR 化，接入微信公众号处理学员提问：

- 学员在公众号提问，RAG 检索课件内容后带出处回答，超纲转人工
- 15 题评测（引用准确 / 边界拒答 / 口语化召回），最终 100% 通过
- 检索匹配率从最初的 5/15 提升到 15/15：写脚本逐条分析失败 case，定位到「长句 AND 匹配过严 + 口语化表达（3k/2米5）与课件书面语不匹配」，通过调整分块策略和同义词映射解决

### 演进对比

| 维度 | 阶段一（Dify） | 阶段二（公众号实际接入） |
|------|---------------|---------------------|
| 知识库 | 16 篇运营文档 | 528 张课件 OCR |
| 接入方式 | Dify Chatflow 内嵌 | 微信公众号 API |
| 用户 | 运营者内部 | 公众号用户 |
| 评测集 | 20 题（运营场景） | 15 题（课件场景） |
| 通过率 | 90%（18/20） | 100%（15/15，样例评测） |
| 匹配率 | — | 5/15 → 15/15（优化分块策略） |

## 平台模块四：AI 日报工作流（每日使用）

> 代码见 [`ai-daily-workflow/`](./ai-daily-workflow) 目录

每天自动完成「搜集 AI 新闻 → AI 主编筛选解读 → 生成《经济学人》风格编辑漫画 → 复古报纸三栏排版 → 微信个人 Bot 推送」，并推送到各私域。

### 架构

**Dify 云版工作流（8 节点）**：定时触发 → Google 搜索 → AI 新闻主编（deepseek-chat，按影响力/稀缺性/趋势/传播评分筛选）→ 解析 JSON → 漫画导演（生成英文图片 prompt，The Economist 风格）→ 通义千问生图（1280×720）→ 整理输出 → 结束

**微信 Bot（Python）**：wechat-ilink-bot 框架，关键词触发 + 每天 8:00 定时推送，HTML/CSS + Playwright 渲染复古报纸排版 PNG

### 样例效果

- 每天自动产出 1 份带编辑漫画的 AI 日报并推送到各私域
- 报纸排版：报头 + 横向通栏漫画 + 三栏（讯息/总结影响/行业意义）
- 复古纸张纹理背景，《经济学人》编辑漫画风格

## 失败案例与迭代

### 失败案例 1：RAG 检索匹配率仅 5/15

- **现象**：课件问答机器人初版，15 题评测只通过 5 题，大量问题检索不到相关课件
- **第一反应**：换更大的模型、增加 TopK 数量——但效果提升有限
- **根因定位**：写脚本逐条分析失败 case，发现是分块策略问题——长句被 AND 匹配过严，口语化表达（「3k」「2米5」）和课件书面语对不上
- **解决方案**：调整分块策略（按语义段落而非固定长度），增加同义词映射
- **结果**：匹配率从 5/15 → 15/15，**没有换模型，只改了分块**

### 失败案例 2：Dify HTTP 节点返回 400

- **现象**：主控 Workflow 串联话术生成器时，HTTP 节点频繁返回 400 错误
- **排查**：对比手动调用成功的请求和 Dify 模板替换后的请求，发现 body 中的 JSON 含换行符时，模板替换会破坏 JSON 结构
- **解决方案**：在 HTTP 节点前加 Code 节点，用 Python `json.dumps()` 预序列化 body，确保转义正确
- **结果**：400 错误彻底消失，全链路稳定运行

### 失败案例 3：AI 日报 V1 四宫格漫画信息分散

- **现象**：V1 版本用四宫格漫画展示每日新闻，用户反馈「看不懂四张图之间的关系」「信息量太散」
- **根因**：四宫格各自独立，没有统一的视觉叙事线；漫画风格不统一，有的写实有的卡通
- **迭代方向（V2）**：
  - 放弃四宫格，改为**单张横向编辑漫画**（The Economist / NYT 风格），用一个画面讲一个核心故事
  - 新增「漫画导演」LLM 节点，专门负责把新闻要点转化为统一风格的图片 prompt
  - 排版改为复古报纸三栏布局，漫画作为通栏主视觉
- **结果**：V2 版本视觉叙事更集中，用户理解成本降低

## 关键产品决策

不是选「最先进的技术」，而是选「最适合这个场景的方案」：

| 决策点 | 选择 | 为什么不选另一个 |
|--------|------|------------------|
| 知识方案 | RAG | Fine-tuning 每周重新训练成本高，且无法引用来源 |
| 应用架构 | Chatflow + Workflow 拆分 | 一个应用会让交互逻辑混乱，且 Workflow 可被 HTTP 串联 |
| 输出格式 | 强制 JSON 输出 | 自由文本无法可靠解析写回飞书字段 |
| 日报漫画 | 单张横向编辑漫画 | 四宫格信息分散，用户理解成本高 |
| 成长值激励 | 奖励「有用」（下载/Fork） | 奖励「认同」（点赞）容易刷分，且不反映真实价值 |

## 架构选型：Workflow 与 Agent 的边界

本项目的四个平台模块并非全部是 Agent，而是根据场景确定性选择了不同的自动化模式：

| 平台模块 | 模式 | 为什么这样选 |
|--------|------|-------------|
| AI 运营平台（周画像+话术） | **Workflow** | 输入（飞书数据+访谈）和输出（9段式画像+3条话术）格式固定，步骤可预设，不需要模型动态决策 |
| RAG 问答机器人 | **Agent（检索+拒答判断）** | 用户问题不可预测，模型需要自主判断检索结果是否相关、是否超纲、是否需要转人工——这是 Agent 的自主决策环节 |
| 实习生工作台 | **确定性表单** | SOP 执行是高度结构化的任务，用表单和规则引擎即可，大模型反而增加不确定性 |
| AI 日报工作流 | **Workflow + LLM 节点** | 搜集→筛选→生图→排版的链路固定，但新闻筛选和漫画 prompt 生成需要 LLM 判断，属于 Workflow 中的模型节点 |

**核心判断**：不是所有 AI 项目都要做成自主规划 Agent。运营自动化场景中，输入输出格式固定、步骤可预设，Workflow 更可靠、可复现、可审计；问答场景中用户意图不可预测，才需要 Agent 的检索和拒答决策。

## 脱离 Dify 的核心逻辑说明

> 本项目以 Dify、飞书 Base App、微信公众号和 Python Bot 组合落地，核心逻辑按业务流程拆分，便于后续维护和替换具体工具。

### 四个平台模块的技术依赖分析

| 平台模块 | 是否依赖 Dify | 脱离 Dify 的实现方式 |

| 平台模块一：AI 运营平台 | 是（Dify Workflow） | 用 Python + 定时任务 + LLM API 重写，核心逻辑不变 |

### 平台模块一（AI 运营平台）脱离 Dify 的核心逻辑

整个周复盘自动化可以拆解为 3 个步骤，每个步骤都不依赖 Dify：

```
输入：本周投放数据（飞书多维表格）+ 用户访谈记录
  ↓
Step 1: 数据汇总（纯代码）
  → 从飞书多维表格 API 读取本周数据
  → 按用户分群、渠道、内容类型聚合
  → 输出：结构化数据 JSON
  ↓
Step 2: 画像生成（LLM API 调用）
  → 把结构化数据 + 访谈原话喂给 LLM
  → 系统提示词定义 9 段式画像模板（用户构成/核心痛点/行为特征/内容偏好/...）
  → 要求每个痛点必须附访谈原话作证据
  → 输出：9 段式群体画像 Markdown
  ↓
Step 3: 话术生成（LLM API 调用 + JSON 解析）
  → 把画像喂给 LLM，系统提示词定义 3 种风格（正式/亲切/活泼）
  → 强制 JSON 输出：{"style_1": "...", "style_2": "...", "style_3": "..."}
  → 解析 JSON，通过飞书 API 写入文案库多维表格
  ↓
输出：群体画像 + 3 条话术 + 自动写回飞书
```

**用伪代码实现：**

```python
def weekly_review_workflow(week_start, week_end):
    # Step 1: 数据汇总（飞书 API）
    data = feishu_bitable.read(
        app_id=APP_ID,
        table_id="投放数据表",
        filter=f"日期 >= {week_start} AND 日期 <= {week_end}"
    )
    aggregated = aggregate_by_segment(data)  # 纯 Python 聚合
    
    # Step 2: 画像生成（LLM API）
    interviews = feishu_bitable.read(table_id="访谈记录表")
    persona = llm.chat(
        system_prompt=PERSONA_PROMPT,  # 9 段式模板 + 证据约束
        user_input=f"数据：{aggregated}\n访谈：{interviews}"
    )
    
    # Step 3: 话术生成（LLM API + 强制 JSON 输出）
    scripts = llm.chat(
        system_prompt=SCRIPT_PROMPT,  # 3 种风格 + JSON 输出格式
        user_input=f"画像：{persona}",
        response_format="json_object"  # 强制 JSON 输出
    )
    scripts = json.loads(scripts)
    
    # 自动写回飞书
    for style, text in scripts.items():
        feishu_bitable.append(table_id="文案库", fields={"风格": style, "文案": text})
    
    return {"persona": persona, "scripts": scripts}
```

**Dify 做了什么、没做什么：**

| Dify 提供的 | 核心逻辑（不依赖 Dify） |
|------------|----------------------|
| Workflow 可视化编排 | 9 段式画像模板和证据约束（系统提示词设计） |
| HTTP 节点调用飞书 API | 飞书 API 调用和数据聚合逻辑 |
| Code 节点处理 JSON | 强制 JSON 输出与解析（`json.dumps` 解决转义） |
| 定时触发 | 用 Python `schedule` 或 cron 替代 |
| 日志和监控 | 用飞书多维表格或简单日志替代 |

**结论**：Dify 负责可视化编排和节点调度；画像模板、证据约束、强制 JSON 输出与解析、数据聚合都在提示词和 Code 节点里，可脱离 Dify 用纯 Python 重写（见上方伪代码）。

### 平台模块二的脱离 Dify 路径

平台模块二的公众号版本按脱离 Dify 的方向完成了重写并接入使用：

- 阶段一用 Dify Chatflow 快速验证（1 天搭完）
- 阶段二按纯 Python + 微信公众号 API 重写，接入 528 张课件 OCR 知识库
- 检索匹配率从 5/15 优化到 15/15，核心是**分块策略和同义词映射**，和 Dify 无关

这说明：Dify 适合快速搭建，接入真实业务后再用代码补足更细的控制。

## 项目反思

这段经历走完了「发现问题 → 定义方案 → 落地工具 → 验证效果」的完整过程。24 份问卷推翻了「发课程 = 提供价值」的假设；检索匹配率从 5/15 到 15/15，靠的是写脚本定位到「长句 AND 匹配过严」这个具体原因并调整分块策略。

这个项目里真正起作用的两次改进——画像附访谈原话作证据、检索改分块策略——都不是换模型，是改了「什么算对」的定义。
